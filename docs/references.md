# 参照資料の要点（docs/references.md）

原文は `docs/sources/`（公開日つきのファイル6本）。ここは**方法レベルの要点**の要約（言い換え）。学び方・段階の判断で迷ったら、この要約ではなく原文を読む。

## 4/13 題材検討〜開発〜収益化 4ステップ（個人開発）
- 題材：自分が本当に欲しいもの。誰にも使われなくても自分が使い続けるものを作る
- 開発：最初に全体をざっくり伝えてAIで完成形まで一気に作り、目で見て解像度を上げてから1つずつ修正する
- MVP：コア機能だけはUI・性能まで磨き切る（大手より使いやすい自信）。補助機能は粗くてよい
- 集客：作る前に初期ユーザーを数人見つけておく。要望には即対応し、紹介が起きるほど満足させる
- 注記：初心者はWeb推奨（ネイティブは審査と年会費のハードル）→本件は加入済みなので該当しない

## 4/22 長く稼ぐための6つの知識（個人開発）
- 書く力はほぼ不要、**読む力は必要**（漢字に例えて、書けなくてもよいが読めないと困る）
- Webの仕組み：リクエストとレスポンスの往復。コードを「入力・出力・演算のどれか」で捉える前提
- フロントとバック：コードがどこで動くか。秘密情報を端末側に置かない判断の土台
- プログラミング基礎：文法暗記は不要。上から順に実行、if（条件分岐）、繰り返し、変数が読めれば十分
- Git：ブランチの概念が最重要。コマンドは覚えなくてよい（AIに頼めばよい）
- DB：最も時間をかける価値がある（テーブル・レコード・リレーション、将来の変更に耐える設計か）
- セキュリティ：入力を信用しない、重要操作の再認証、バックアップ、本番でエラー詳細を見せない
- SEO/OGP：Web向け（本件では優先度低）

## 5/07 新しく始める個人開発のロードマップ（個人開発）
- 題材は自分の苦手・課題から。類似サービスを調べ、日本で手薄な立ち位置を探す
- **プロダクトより先に集客チャネルを作る**：発信を通じてペルソナとのずれを埋めてから作る

## 6/04 個人開発とチーム開発で必要なスキル
- 個人開発：何を作るかの判断力、AIで素早く形にする、作り込まない割り切り、届けて稼ぐまでやり切る
- 会社開発：品質・信用を守る力（本件は対象外）
- 両方の土台は**コードを読む力**。ここだけはショートカットしない

## 7/02 ゼロから個人開発を始めるなら（個人開発）
- 学ぶ優先順位：**API・DB・Git**。AIの出力を監視し方向づけるための知識
- Git：こまめにコミット、ブランチ、プルリク、差分をざっと読んで変更を理解する運用が必須
- **AIを学習の代わりにしない。加速装置として使う。バグや謎のエラーを全部学習機会にする**
- 題材は自分が直面している課題。マーケティングは開発より先・並行（デモやログを発信）

## 10/05 システム開発をゼロから学ぶ手順（※目的が違う：仕事を任されるための学習、Web前提）
- 4段階でAIの役割を変える：書き手 → 家庭教師 → 同僚 → 相棒
- 段階1でも「動作確認は自分の目で、AIの変更は読んでから承認」
- 公開したら一度立ち止まって自問：「ボタンを押すと裏で何が起きるか」「データはどこに保存されているか」等
- わざと少し壊して直す → 赤いエラーは道案内だと体感する
- 家庭教師モード：答えのコードは書かず、ヒントを1つだけ出し、本人の答えを判定する
- 段階4：誰がいつどう使うかを書き出し、コア機能を3つに絞り、**作らない機能も書き残す**。空のアプリを先に公開し、1機能ずつプルリク。最低1人に使ってもらいフィードバックを1件反映
- 約300時間は仕事向けの目安（本件には不適用）
